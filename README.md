# 场景切换器（SillyTavern Scene Switcher）

一个独立的酒馆外部扩展。把常用的 **酒馆原生 API 连接配置、角色卡、API 原生预设、酒馆主题** 保存为“组合”，以后用一项快速切换。

它只改动你在组合里明确勾选的项目；没有勾选的项目完全保持当前状态。

> [!IMPORTANT]
> 这是用户级第三方扩展，不修改 SillyTavern 核心文件，也不隶属于 SillyTavern 官方。它管理的是酒馆已有资源和设置的“切换入口”，不是完整备份工具。重要聊天、角色卡和预设仍应使用酒馆自身或其他备份方式保存。

## 适用范围与工作方式

- 当前开发与验证基线为 SillyTavern `1.18.x`。
- 扩展启动后会检查它需要的酒馆原生入口；缺失、改名或不可用时，对应操作会显示诊断并停止，不会猜测字段或直接改写酒馆配置文件。
- 场景切换只保存资源引用和用户选择的绑定项目，不复制角色卡正文、聊天正文、世界书正文、预设正文或其他扩展设置。
- 本扩展不替代酒馆原生功能：角色、预设、主题、聊天、人设和 API 仍由酒馆执行实际切换；扩展只负责让这些操作可组合、可预览和可追溯。

## 现在能做什么

- 在“保存当前组合”后按需取消勾选 API 连接配置、角色、预设或主题。
- 将常用组合置顶到“常用组合”抽屉。
- 从底部抽屉搜索角色卡。搜索会防抖，结果每页显示 12 项，适合角色很多的库。
- 角色选择器可搜索酒馆标签与角色卡内标签，并可只看收藏角色。
- 可按当前角色或当前群聊搜索、切换酒馆原生聊天记录；聊天记录不会写入组合，避免误切旧对话。
- 在“快速替换”抽屉中临时切换一项，不会自动覆盖其他项目。
- 切换组合前会先显示“本次会变什么”；默认开启，可在设置中关闭。不会列出的项目不会被读取或写入。
- 组合切换中途失败时，会只恢复已经确认可安全恢复的 API、连接档案、角色或预设；主题不会被盲目回滚，以免再次覆盖个人美化偏好。
- 记录最近使用的角色与最近 20 次切换；可对有明确原生恢复路径的项目一键撤回。
- 可选开启聊天页的“快速切换悬浮球”，直接打开常用组合、角色、聊天记录、API、预设和美化；默认关闭。菜单面板继承酒馆主题，悬浮球本体可选珊瑚橘、青绿、鸢尾紫或鎏金配色。
- 点击组合时会先检查所有目标是否仍存在；检查失败时不会开始切换，避免出现半套配置。
- 防止重复点击触发并发切换。
- 在“主题切换偏好”中自行勾选要继承的个人美化与聊天显示习惯；默认保留模糊、阴影、字体、宽度、头像与自定义 CSS，主题配色仍按新主题切换。

- 聊天记录选择器同样每页只渲染 12 条，翻页与搜索只更新结果区域。
- 可给已保存组合设置分组；若酒馆更新或资源删除导致绑定目标不存在，组合会标出缺少的项目，可从右侧编辑入口重新绑定。
- 悬浮球拖动使用每帧一次的位置刷新，降低移动端拖动时的布局计算。
- 组合应用后会显示“已替换、保持不变、失效且未执行”的结果；失效绑定会阻止整套组合写入，避免留下半套设置。
- 场景卡可直接复制；编辑页可改名或“另存为”副本，原组合不会被覆盖。
- 悬浮球可选单击或长按展开；关闭时会移除悬浮球节点及其事件监听。
- 用户人设选择器调用酒馆原生 `setUserAvatar()`；与当前角色卡（或群聊）绑定的人设排在前面，可展开只读查看完整描述，不保存或复制人设正文。
- 角色与人设缩略图使用浏览器懒加载；重复的聊天记录搜索会在短时间内复用结果，避免重复请求。

## 场景、快速替换与原生联动的区别

| 入口 | 会修改什么 | 不会修改什么 |
| --- | --- | --- |
| 保存的场景组合 | 仅修改该组合中勾选的 API、角色、预设、主题或用户人设 | 未勾选项目、聊天记录、其他扩展设置 |
| 快速替换 | 只修改你这次选中的单项 | 不会自动套用某个场景的其余项目 |
| API 管理器 | 仅 API Custom 的连接字段与酒馆原生密钥引用 | 预设、角色、主题、正则、代理和其他扩展设置 |
| 聊天记录选择器 | 仅打开已存在的酒馆聊天记录 | 不写入场景，也不更换 API、预设或主题 |

预设、角色卡本身可能带有酒馆原生的正则、世界书或 TavernHelper 绑定。扩展不会另行“强制切换”这些内容；它只调用酒馆原生的角色或预设选择路径。若酒馆在原生规则下应用了该资源自带绑定，那是酒馆资源本身的行为，不代表本扩展额外修改了全局正则、世界书或其他插件设置。

## 有意不做的事

- 不保存 API 密钥、代理密码或任何连接凭据。
- 不复制整份酒馆设置，也不恢复其他扩展的设置。
- 不自己读写模型、URL 或密钥字段。它使用酒馆内置“连接档案”切换；配置中的模型、URL 和密钥引用仍由酒馆原生管理。

## API 管理器（仅 API Custom）

在“API 管理器”中点“新建 API 配置”，填写名称、Server URL、模型和 API Key。保存后，条目会显示在列表和“快速替换”中；点击即可切换。

- 只支持酒馆的 `API Custom（OpenAI 兼容）`，不会假装兼容其他供应商的专有字段。
- 切换只写入酒馆原生的 API 类型、Custom URL、Custom 模型和当前密钥；不会调用预设、角色、主题、正则、代理或其他扩展的切换逻辑。
- API Key 通过酒馆原生 `Secrets` 写入服务端密钥存储；扩展设置只保存其 ID，绝不保存明文密钥。编辑时留空密钥会沿用旧密钥；删除配置只删除扩展中的引用，不会删除酒馆里的密钥。
- 若酒馆升级后缺少所需原生控件，切换会提示兼容性错误并停止，不会尝试猜测或写入其他设置。
- 每条 API 配置旁的“测”会先应用该条目的四项 API 数据，再点击酒馆原生“连接”按钮；连接成功或失败仍由酒馆原生状态提示显示。
- 最近 5 次 API 测试会显示成功、失败或“未确认”和时间；“未确认”表示 12 秒内未观察到酒馆原生连接状态变化，必须以酒馆顶部状态为准。
- “从酒馆连接档案导入”可读取现有档案，即使原档案绑定了预设、代理或正则；导入时只抽取 API、Server URL、模型和密钥引用，其他字段不会进入 API 管理器。

## 使用方式

1. 先在酒馆原生界面手动调整到你想保存的状态。
2. 打开“场景切换器”，点击“保存当前组合”。
3. 若要只切换 API 配置，点击“＋ 新建仅 API 连接配置”。酒馆原生窗口会自动只保留 API、Server URL、Model、Secret；预设、代理、正则、停止词和提示词等都会自动取消，因此切换时不会改其他设置。若你明确要让某套配置同时切换代理，再手动勾选 Proxy 即可。
4. 若希望显示在顶部，把它设为“常用组合”。
5. 之后直接点该组合即可应用。未勾选的项目不会读取、校验或写入。

在“快速悬浮球”中开启显示后，聊天页会出现一个小型入口。轻点可打开角色、聊天记录、API、预设、美化和常用组合；拖动可随意换位置，位置会保存在本扩展设置中。API、预设和美化分别走其原有的单项切换路径，不会连带其他设置。预设列表只显示当前对话模式对应的酒馆原生预设，选择预设不会切换 API。

角色选择器默认按收藏、最近使用和名称排序。搜索结果每页只显示 12 项，搜索或收藏筛选变化会自动回到第 1 页；可用固定的上一页/下一页翻阅，不会一次性渲染整个角色库或把角色卡挤压、拉伸。

可在同一设置中选择悬浮球色系，并填写 HTTPS 图片直链作为图案。扩展只接受 HTTPS 地址；图片无法加载时会自动显示默认闪电图标，不影响切换功能。

打开“主题切换偏好”可自行选择要继承的字段，选择会立刻保存到扩展设置。切换“主题”前，扩展会显示确认窗口。选择“保留个人偏好后切换”不会保存旧主题，也不会打开酒馆的主题命名输入框；它在应用目标主题后仅恢复你已勾选的项目。选择“按新主题完整切换”则按酒馆原本行为应用目标主题。

## 兼容与安全边界

本扩展不替换、不拦截酒馆函数，也不模拟鼠标点击。它只通过酒馆已有的原生路径执行：

- API 连接配置：只列出不含预设、正则或提示词项的酒馆原生连接档案。扩展写入原生 `#connection_profiles` 下拉框并触发其 `change` 事件；酒馆负责应用 URL、模型和密钥引用，扩展不会调用预设切换。
- API 类型（备用）：写入原生 API 下拉框并触发其 `change` 事件。
- 角色：调用酒馆的 `selectCharacterById()`。
- 预设：调用酒馆的 `getPresetManager(api).selectPreset()`。

如果当前酒馆版本缺少以上原生入口，扩展会提示不接管任何设置，而不是猜测字段或强行改写配置。

“兼容性与诊断”抽屉会逐项显示角色、预设、主题、聊天记录、连接档案和 API Custom 所需的原生入口是否可用。它不读取密钥内容，便于酒馆更新后判断是上游接口变化还是配置本身有问题。

已保存的组合仅存放在酒馆扩展设置中，内容是名称、角色头像文件名、预设名、主题名和 API 类型；不含聊天记录、角色卡正文或密钥。

## 重要注意事项

### 切换前与失败时

- 场景在开始前会检查目标角色、预设、主题、连接档案和用户人设是否仍存在。任一已勾选目标缺失时，整套组合不会开始写入，避免得到“半套场景”。
- 执行过程中发生错误时，扩展只回退已确认具备独立原生恢复路径的项目；主题不会被盲目回滚，因为再次应用主题可能覆盖你的个人美化偏好。
- 切换结果会区分“已替换、保持不变、失效且未执行”。请以该结果为准；不要把“点击了组合”理解成所有项目一定都已成功写入。
- 不要在切换正在进行时反复点击场景卡、悬浮球或浏览器返回。扩展会拒绝重复触发，但等待当前操作结束最稳妥。

### API 与密钥

- API 管理器只支持 `API Custom（OpenAI 兼容）`。其他供应商的专有字段没有被伪造为“已支持”。
- API Key 由酒馆原生 Secrets 管理；扩展设置只保存密钥引用，不保存明文。不要把密钥、反代地址、完整控制台日志或设置导出直接发到公开问题区。
- “测试连接”会让酒馆原生界面执行连接测试。若结果显示“未确认”，表示扩展在 12 秒内没有观察到酒馆状态变化，不等于连接一定成功或失败，应以酒馆顶部原生状态为准。
- 删除 API 管理器条目只删除本扩展的引用，不会删除酒馆的原生密钥；需要清理密钥时请在酒馆原生 Secrets/连接配置中操作。

### 主题、角色、预设与聊天

- “保留个人偏好后切换主题”只恢复你主动勾选的偏好字段；没有勾选的外观字段会按目标主题生效。它不保存旧主题，也不会把旧主题完整叠加到新主题上。
- 切换角色或打开聊天可能改变酒馆当前的活动角色/聊天上下文，但不会更改 API、预设、主题或场景之外的设置。
- 聊天记录不会保存进场景组合。这是刻意设计，避免点击常用组合时意外跳回旧聊天。
- 删除或改名酒馆中的角色、预设、主题、连接档案或人设后，已保存组合会保留失效引用并提示重新绑定；扩展不会自动替换为同名资源。

### 与酒馆更新、其他扩展共用时

- 酒馆升级后，如果原生控件、公开函数或连接档案结构变化，相关功能可能显示“不兼容”或不可用。这是保护措施；请不要通过修改选择器、强行启用或手改扩展设置绕过它。
- 本扩展不主动读写其他扩展的设置，也不会把其状态加入场景；但其他扩展若监听酒馆原生的角色、预设或主题切换事件，仍可能按自身逻辑响应。
- 如遇问题，请先在可丢失的测试角色和聊天中复现，并保留原始资源备份。不要用唯一的重要聊天来验证切换、主题或 API 配置。

## 二次开发指南

如果原项目后续不再维护，其他开发者可以在遵守 [PolyForm Noncommercial License 1.0.0](LICENSE)、且用途属于非商业范围的前提下 fork 本仓库继续维护。请先阅读本节、README 的兼容边界和现有测试；不要只根据“场景切换”这个名称重写一套会广泛修改酒馆设置的切换器。

### 开始前

1. fork 仓库并在独立分支开发，保留可回退的 Git 历史；
2. 运行 `npm run check`，确认修改前基线通过；
3. 阅读 `index.js`、`modules/SceneModel.js`、`modules/SceneRecovery.js`、`modules/ApiOnlyProfile.js` 和对应测试，确认场景数据、执行顺序、回退边界与 API-only 限制；
4. 在目标 SillyTavern 版本中核对实际公开函数、原生控件和连接档案行为；
5. 先用可丢失的角色、聊天和 API 测试配置复现，再修改实现；不要以唯一的重要聊天或唯一密钥做测试。

### 必须保留的安全边界

1. **只修改已勾选绑定。** 场景、快速替换和 API 管理器必须保持明确的写入范围；不能为了“方便”把未勾选的预设、正则、主题、聊天或其他扩展设置一起带入。
2. **先全量预检，再开始写入。** 任一已勾选目标不存在或原生入口不可用时，应停止整套场景，不能留下半套设置。
3. **API 密钥只保留酒馆原生引用。** 不得把 API Key、代理密码、Cookie 或明文 Secrets 写进扩展设置、日志、场景、测试夹具或 GitHub 问题。
4. **保持 API-only 边界。** API 管理器只处理已审计的 API Custom 连接字段和密钥引用；不要把预设、正则、提示词、停止词或供应商专有字段伪装成“API 切换”的一部分。
5. **切换必须串行。** 不得移除进行中操作拦截，也不要用多个异步切换同时写入同一份酒馆状态。
6. **回退必须有证据。** 只回退具有独立原生恢复路径的项目；主题和个人美化偏好不能在失败后盲目再次应用。
7. **不复制其它扩展状态。** 本扩展可以调用酒馆原生的角色、预设、主题、聊天和人设入口，但不能接管或持久化其他扩展的私有设置。
8. **聊天不进入场景。** 除非另行设计、审计并获得用户批准，不要把聊天记录作为场景自动绑定项；误跳回旧聊天的风险高于这项便利。

### 适配新的 SillyTavern 版本

增加或重新声明对新酒馆版本的支持前，建议按以下顺序进行：

1. 核对角色、预设、主题、用户人设、聊天和连接档案的真实原生入口是否仍存在；
2. 核对连接档案切换是否仍可能连带预设、正则或代理，确保 API 管理器继续只提取允许的连接字段；
3. 在可丢失测试数据上分别验证单项切换、完整场景、缺失目标预检、切换失败和重复点击；
4. 为变化的入口补充“正常路径”和“入口缺失时不写入”的成对回归测试；
5. 更新 README 中的验证基线、兼容提示、`manifest.json` 版本和变更记录，不能只为了消除“不兼容”提示而放宽检查。

如果上游版本已经改变某项原生语义，正确做法可能是让该项显示“不兼容”并停止切换，而不是用直接字段写入或模拟点击绕过酒馆。

### 修改 UI 与性能时

- 悬浮球、抽屉、角色/聊天/人设选择器必须优先保证移动端可用，不能只按桌面宽度调整；
- 长角色库和聊天列表继续保持搜索、分页、懒加载和局部更新，避免搜索时重建整个设置面板；
- 不要把悬浮球重新做成固定位置、持续高频布局写入或无法关闭的全局节点；
- 不要把“已加载扩展”误写成“已成功应用场景”。结果面板、缺失项和兼容性诊断必须与实际执行结果一致；
- UI 变化后至少在竖屏移动端与桌面端检查弹层位置、滚动、关闭、横向溢出和可点击性。

- [ ] `npm run check` 全部通过；

- [ ] 发布时遵守本仓库的发布快照流程，不将本地开发历史误推到 GitHub `main`。

## 发布维护：GitHub 只保留一个发布提交

本仓库刻意区分“本地开发历史”和“GitHub 发布快照”：本地 `main` 保留完整提交，GitHub `main` 只保留当前版本的一条无父提交快照。因此 GitHub 安装地址始终简洁，不会公开开发过程中的历史提交。

每次发布按以下顺序操作：

1. 在本地正常提交本次修改，并先运行 `npm run check`；
2. 确认工作区干净；
3. 在仓库根目录运行：

   ```powershell
   .\scripts\Publish-ReleaseSnapshot.ps1
   ```

脚本会读取当前已提交文件树，生成新的根提交，更新本地 `release-snapshot`，再用 `--force-with-lease` 覆盖 GitHub 的 `main`。它不会切换、重写或删除本地 `main` 的开发历史；工作区有未提交文件、远端分支在拉取后发生变化或远端不存在时会停止。

不要直接运行 `git push origin main`，否则本地开发提交会出现在 GitHub。这个脚本只应由仓库维护者用于发布默认分支。
